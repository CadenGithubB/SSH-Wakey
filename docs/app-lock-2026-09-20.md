# App Lock implementation and validation — 2026-09-20

This extends the local [security hardening review](security-hardening-2026-09-19.md).
The requested policy is five minutes without input delivered to SSH-Wakey, with
SSH disconnection on lock. The feature is opt-in for the standard encrypted
connection vault. Validation used an isolated temporary vault; no production
vault was migrated or release installed.

## Behavior

- A protected vault starts locked. Touch ID or the Mac login password is handled
  by macOS. The recovery passphrase provides independent access and preserves
  App Lock. Remote SSH passwords are never cached by this feature.
- Five minutes of app inactivity, screen lock, sleep, user switching, Lock Now,
  or Shift-Command-L revokes access. Terminal activity does not renew the lease.
- Revocation cancels authentication and SSH attempts, disconnects existing
  transports, releases the open vault key and connection list, clears diagnostic
  state, and dismisses editors. Unsaved changes are discarded. An owned recovery
  clipboard copy is cleared only if it has not been replaced.
- Unlocking never reconnects an old session. Captured menu actions, native field
  submissions, delayed network work, and authentication completions cannot revive
  the authorization that existed before locking.

## Cryptographic and memory boundary

The local wrapping key is derived through a user-presence-protected Secure
Enclave P-256 key-agreement operation and HKDF-SHA256. The stored representation
is an opaque device-bound key blob. No permanent Data Protection Keychain item
or provisioning entitlement is required by this backend. Unsupported hardware
refuses enablement; it does not silently use an unprotected key.

Vault format 2 uses separate authenticated-data domains for payload, local-key
wrapper, and recovery wrapper. All authenticate the protection mode. The local
wrapper additionally authenticates its hardware metadata. Damaged hardware
metadata therefore blocks that slot while preserving recovery; an unknown or
changed protection mode cannot silently downgrade authentication. Format 1
remains readable, and older readers refuse format 2.

Enablement, disablement, and passphrase replacement rotate the data key and use
revision-checked atomic writes. The previous login-Keychain key is deleted only
after protected enablement commits. A stale key cannot open newly rotated data;
old vault copies remain readable with their old credentials.

Recovery proof now authenticates the actual payload, rather than merely
unwrapping any key in the recovery slot. This closes an additional issue where
an attacker-substituted recovery slot could otherwise authorize export or a
security change with an unrelated data key.

Recovery text is processed synchronously before a system-authentication await.
Prepared operations retain only owned key objects and sealed material. Fresh
LAContext instances disable Touch ID reuse and are invalidated on completion or
lock. Operation generations, cancellation checks, and file revisions reject
late results. The lease uses a monotonic clock including sleep; late input
cannot renew an expired lease.

The Secure Enclave private key is nonexportable. Derived symmetric keys and
decrypted connection data necessarily exist in app memory while open. Releasing
Swift, AppKit, and CryptoKit objects does not prove physical erasure of every
framework-owned allocation. App Lock does not protect a compromised operating
system, erase Terminal scrollback, stop detached remote jobs, or revoke backups.
Its timers and cleanup require the app process to run. Crash/force-quit cleanup
of an orphaned SSH master occurs on next launch, rather than through a separate
watchdog.

## Validation

At completion of the App Lock stage, the standard and managed suites each passed
**384 tests, zero failures**, including the final authentication-context cleanup.
This added 41 tests to the prior 343-test security-hardening baseline. Subsequent
[password-helper sandbox work](password-helper-sandbox-2026-09-20.md) brings the
complete suite to **388 tests** in each configuration.

Standard Release and ManagedRelease builds passed for both arm64 and x86_64.
The shared release guard passed strict signature verification on both
architectures, required Hardened Runtime, and rejected development/runtime
exception entitlements. These are locally ad-hoc-signed verification builds,
not Developer ID-signed or notarized distribution artifacts.

Tests use synthetic credentials, isolated directories and named test pasteboards.
Lifecycle tests post local notifications without actually sleeping or locking
the workstation. The tests include late successful authentication after lock,
cancelled preparation, concurrent file changes, old-key retirement, independent
recovery, protected-mode tampering, substituted recovery slots, stale SSH work,
expired input events, and clipboard ownership.

Native checks exercised protected enablement, Lock Now, the keyboard
shortcut, recovery unlock preserving App Lock, and cancellation of a subsequent
system unlock. The native flow used an isolated temporary vault. A separate
synthetic Secure Enclave probe verified that key use with authentication
interaction prohibited is denied. No real remote SSH connection was needed for
these App Lock checks; session revocation is covered by regression tests.
